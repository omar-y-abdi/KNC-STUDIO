### F1 — real WebKit close loses a pending production-size canvas edit; synthetic test misses it (P2)

**Verified behavior:** load the stored production-size fixture into Studio, reach a clean publication, give the top page a real click (sticky user activation), pause the clock before the editor's180ms handoff/backup500ms debounce, change an actual Grapes text component, and call real `page.close({runBeforeUnload:true})`. Chromium raises one beforeunload prompt and its IndexedDB record contains the edit while that prompt remains open. WebKit raises no prompt, closes, and the edit is absent from every IndexedDB record after five seconds. A fresh tab has no sessionStorage journal by design. Browser “reopen closed tab” session restoration was not tested and is a different guarantee.

**Cause evidence:** `Studio.tsx:303-311` performs full `editor.flush()` / draft scheduling / serialization before returning from beforeunload. The app's early marker sees user activation true and defaultPrevented false; its late marker sees defaultPrevented true500ms later, followed by pagehide and visibility hidden. Root's independent small-page WebKit control prompts for a fast handler with/without a paused clock;200ms busy work suppresses the prompt whether cancellation is set first or last, and1000ms work can be interrupted. Therefore neither fake-clock absence of activation nor simply moving preventDefault earlier explains or repairs the issue.

**Main comparison:** same immediate pending-canvas-edit boundary also loses the edit on archived main (legacy localStorage checked). Main has no lifecycle handler; its early/late markers both show defaultPrevented false in the same millisecond. This is an existing narrow data-loss gap that PR90's new close-preservation feature fixes in Chromium but leaves unresolved in WebKit, rather than a newly introduced loss at this exact boundary.

**Test gap:** `tools/e2e/cms-lifecycle.spec.mjs:402-414` substitutes a synthetic beforeunload event in WebKit, waits for IndexedDB while the page stays open, then closes. That proves handler intent, not the test title's actual close warning/durability contract. An all-green WebKit baseline cannot dismiss this finding.

**Repair boundary:** keep the close decision cheap enough to return promptly; expose existing pending-editor state if needed instead of serializing a full canvas before asking. A standard warning must allow Cancel/dismiss to retain the live edit and let normal backup finish; verify that actual close path in both engines with the production-size fixture. Do not promise durability after the user chooses Leave unless a real test proves it. Deferring heavy capture while a modal is open may not run on all engines and needs evidence. Preserve existing reload/background journal and all closed-tab offers. Do not weaken the test to synthetic events.

Evidence: `04-real-close.spec.mjs`, `real-close-controls.log`, `real-close-markers-head.log`, `real-close-markers-main.log`, `restore-race-results/04-real-close-a-real-immed-8a3a9-production-size-canvas-edit-webkit/trace.zip`, and `real-close-main-results/`.

### F2 — closed-tab recovery overwrites a new edit made while state reload waits (P2, introduced)

**Exact reproduction:** persist an unpublished closed-tab page named `Closed tab draft`; open a clean receiving Studio; choose `Visa utkast` / `Fortsätt här`; intercept and hold the ensuing `cmsApi.state` request; fill the still-enabled `Namn` textbox with `Newer recipient edit`. Before releasing the request, the sidebar renders that new name and `.cms-revert` becomes enabled (it is disabled exactly when `!draft.dirty`; the busy status itself says `Arbetar…`). Release the state request and await the actual `Ett lokalt utkast ... återställdes` notice. The name then becomes `Closed tab draft`; the newer edit has been replaced.

**Cause:** `Studio.tsx:563-582` checks the receiver is clean only before awaiting `session.adopt`, then calls `refresh`. The existing draft remains interactive during those awaits. `refresh` later constructs and unconditionally installs a new draft at lines151-208, with no check of the edits accepted since recovery began. The backup's offered-record Web Lock/version checks protect the offered record; they do not protect this receiving editor.

**Main comparison:** archived main has only initial own-tab `loadBackup` recovery and no `restoreOffer`, `Visa utkast` or `Fortsätt här` path. This specific newly introduced closed-tab recovery interleaving is absent there. Earlier temporary probes that asserted before the recovery notice were premature and are rejected as evidence; the strengthened completed-refresh reproduction is the accepted one.

**Repair boundary:** flush pending receiving-canvas work before deciding it is clean; prevent simultaneous restore operations; hold a specific restoring state through adoption and refresh so the receiving editor cannot accept edits that will be discarded, or preserve/reconcile any accepted edit explicitly. Do not globally prohibit editing during publication, which is intentionally supported by the draft merge flow. A late dirty check alone after consuming the offer is insufficient: preserve both the offered record and current work if the transition aborts. Review failure/retry handling and dismissal of the recovery dialog as part of the narrow transition.

**Required regression:** hold the state response after selecting recovery, prove normal editable controls are blocked or edits are preserved, then complete recovery and inspect the restored content. Include a pending canvas edit before clicking recovery, two attempted restores, and a failed state reload so no offered draft silently disappears. Existing pure backup lock tests do not cover the receiving Studio interleaving.

Evidence: `04-restore-race.spec.mjs`, `restore-race-strengthened.log`, `restore-strengthened-results/04-restore-race-closed-tab-e3530-er-edit-made-during-refresh-chromium/trace.zip`. Reproduction uses isolated local archive and network guard; original checkout remains unchanged.
