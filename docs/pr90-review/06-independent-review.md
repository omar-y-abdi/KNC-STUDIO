### B-02 — post-lock owner revocation guard removed (P2, verified)

- Changed boundary: `supabase/migrations/20261024140500_cms_publish_single_pass_and_retention.sql:32–50`. The merged publisher checks the owner before acquiring all content locks and the `cms_site` row lock, then writes without rechecking. Frozen main's wrapper took those locks and invoked its unchecked writer, which repeated the owner guard before writes/replays.
- Independent controlled PostgreSQL 16 comparison: `/tmp/knc-backend-repro/owner-race.py` extracts verbatim frozen-main wrapper/writer bodies, renames only their function/call names for side-by-side isolation, uses the existing actual-routine fixture, and runs both against a separate disposable Unix-socket database. It holds `barbers` in ShareRowExclusive mode, observes the publication waiting through `pg_stat_activity`, commits an owner-profile revocation, then releases the table lock. Each publication transaction rolls back. The database is dropped after the test.
- All three revocations (`account_enabled=false`, `must_change_password=true`, `role='barber'`) produce the same before/after result: baseline rejects with `CMS owner required` at the second guard; maintenance succeeds and returns revision 1. This is evidence of the original guard's reachable protection even though neither version promises total serializability against every possible later revocation.
- Recommended minimal repair: restore `perform public.internal_cms_assert_owner(p_actor)` after both table locks and the `cms_site ... for update` lock, before replay or mutations, in a new migration. Keep the single-pass document build optimization. Add a deterministic blocked-publication/revocation regression; test all three owner predicates or at least account disable with the same shared guard.
- Classification: verified regression, P2. Requires an already-authorized request waiting while its actor is revoked; no unauthenticated access claim. No production access was involved.

### B-01 — confirmed, but initial backslash-only repair direction is insufficient

- Independently inspected the full old TypeScript publication validation and the actual PostgreSQL extractor/prune/usage/transition routines. Existing published content is the relevant upgrade boundary; rejecting future noncanonical publication cannot repair an already-persisted head.

A raw backslash guard over actual markup/CSS string values covers these, including native metadata's JSON escapes, without implementing a CSS parser in SQL.
- **Additional reproduced gap:** `/storage/v1/./object/public/...`, `/storage/v1/%2e/object/public/...`, `/storage/v1/unused/%2e%2e/object/public/...`, and `/storage/v1/unused/.%2e/object/public/...` all normalize to the same URL in the old validator while preserving noncanonical stored HTML/CSS. The current raw-prefix index and guard miss them. Raw `images/./kept.webp` indexes the wrong path; `images/extra/../kept.webp` is rejected by the extractor's path filter rather than protecting the normalized target.
- Actual PG16 rollback-only specs `retention-dot-gap.sql` and `retention-percent-dot-gap.sql` each pass all five old-history/asset-protection preconditions and fail the same four post-prune safety assertions as the original CSS escape. Their `*-pg16.log` files preserve output. `retention-dot-gap.mjs` additionally proves old complete-document/media validation accepts the stored dot-prefix fixture and current Edge rejects it.
- Rejected counterexamples: HTML decimal/hex character references in `img src` normalize to canonical literal characters during parse5 serialization and remain indexed; arbitrary `%6f` in `/storage/` is rejected by old resource validation; raw tab/newline and decoded HTML tab entities are rejected. Percent encodings after the literal prefix were already caught by the maintenance guard. A CSS escaped slash immediately before an otherwise literal `/storage/` remains visible to the SQL substring index.
- Minimal repair acceptance: inspect the actual extracted page/region HTML and light/dark CSS values, and conservatively stop pruning for backslashes and raw/percent-encoded dot-segment forms anywhere in those sources, while retaining the existing path percent/entity checks. An even broader percent-escape guard is safe but pauses retention for more harmless source content; document the choice. Do not scan JSON serialization for every backslash because ordinary quotes/newlines serialize as escapes. Do not scan unrelated site prose/settings merely because they contain a backslash. Cover normal quoted HTML, multiline CSS, harmless source escapes, unrelated prose escapes, all four page variants, regions, and successful pruning after canonical republication. A new migration must replace the guard without rewriting history.

### Frontend repairs challenged after reviewer04's real-browser evidence

- **F1 accepted with precise scope.** Read reviewer04's actual-close reproduction, minimal controls and current lifecycle test, then traced Studio lifecycle, Editor timer/export and CmsDraft serialization. The production-size WebKit handler performs expensive canvas export before returning; calling preventDefault early alone does not repair the observed prompt suppression. Frozen main also loses this narrow immediate-close edit, so classify it as an existing loss left unresolved by the new protection, not a newly introduced data-loss regression. The existing synthetic WebKit dispatch keeps the page alive until IndexedDB commits and cannot prove real-close protection.
- The proposed beforeunload handler should read only the existing Editor pending-timer flag and BackupSession.unsaved(), with dirty fallback only if the backup session is unavailable, then cancel/return. Do not serialize, schedule, export or flush in this handler. In the actual input-to-close event path, immutable draft mutation completes before the next user event and the layout effect schedules that draft; the pending timer covers the preceding canvas handoff window. Existing background/pagehide persistence remains separate. Acceptance is an actual activated close in both engines: prompt, dismiss, resume timers, independently observe IndexedDB durability, close without another prompt, recover in a new tab. Create the inspecting page before the edit so its activation cannot accidentally flush the editor. Do not claim IndexedDB commits while a modal is open, or that choosing Leave guarantees preservation.
- **F2 accepted as a verified new race.** Read the strengthened reproduction and its failed final assertion: real locator.fill changed the receiving tab's name, enabled dirty-only revert and changed the sidebar while the state response was held; after the response and actual recovery notice, the name reverted to the offered draft. Parent independently reproduced the same result. Source confirms restoreOffer checks clean only before await, then refresh unconditionally replaces the draft. BackupSession.adopt copies into the receiving tab and consumes the offered copy before refresh; a late setDraft identity check alone is insufficient protection of both drafts.
- The bounded proposed repair is sound for that interactive race: flush the canvas before checking clean, reject while busy/restoring, set restoring/busy before the first await, temporarily render the existing loading view through adoption and refresh, and reset state in finally including stale/error exits. Disable the loading-view exit while restoring; leave ordinary publication's editable-during-request behavior unchanged. Existing opening of the backup view already flushes the canvas, so the additional entry flush is defensive. Implementation acceptance still requires the held-response browser regression to prove authoring is unavailable during restoration, followed by successful restoration and normal editing after it completes. These are proposal assessments; implemented code and current-head results remain to be reviewed.
