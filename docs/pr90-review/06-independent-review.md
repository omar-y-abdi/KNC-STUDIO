## Findings and disposition

### B-02 — post-lock owner revocation guard removed (P2, verified)

- Changed boundary: `supabase/migrations/20261024140500_cms_publish_single_pass_and_retention.sql:32–50`. The merged publisher checks the owner before acquiring all content locks and the `cms_site` row lock, then writes without rechecking. Frozen main's wrapper took those locks and invoked its unchecked writer, which repeated the owner guard before writes/replays.
- Independent controlled PostgreSQL 16 comparison: `/tmp/knc-backend-repro/owner-race.py` extracts verbatim frozen-main wrapper/writer bodies, renames only their function/call names for side-by-side isolation, uses the existing actual-routine fixture, and runs both against a separate disposable Unix-socket database. It holds `barbers` in ShareRowExclusive mode, observes the publication waiting through `pg_stat_activity`, commits an owner-profile revocation, then releases the table lock. Each publication transaction rolls back. The database is dropped after the test.
- All three revocations (`account_enabled=false`, `must_change_password=true`, `role='barber'`) produce the same before/after result: baseline rejects with `CMS owner required` at the second guard; maintenance succeeds and returns revision 1. This is evidence of the original guard's reachable protection even though neither version promises total serializability against every possible later revocation.
- Recommended minimal repair: restore `perform public.internal_cms_assert_owner(p_actor)` after both table locks and the `cms_site ... for update` lock, before replay or mutations, in a new migration. Keep the single-pass document build optimization. Add a deterministic blocked-publication/revocation regression; test all three owner predicates or at least account disable with the same shared guard.
- Classification: verified regression, P2. Requires an already-authorized request waiting while its actor is revoked; no unauthenticated access claim. No production access was involved.

### B-01 — confirmed, but initial backslash-only repair direction is insufficient

- Independently inspected the full old TypeScript publication validation and the actual PostgreSQL extractor/prune/usage/transition routines. Existing published content is the relevant upgrade boundary; rejecting future noncanonical publication cannot repair an already-persisted head.
