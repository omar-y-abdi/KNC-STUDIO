## Write authority and rollout dependencies

The database boundary is authoritative, including for an authenticated owner using REST directly.
After the authority migration, `site_content`, `about_content` and `email_templates` reject direct
authenticated inserts, updates, deletes and upserts. CMS content settings also require publication.
The sole direct owner `site_settings` exception is `cancellation_policy_hours` (1–168 whole hours).
It remains outside CMS history, revision and fingerprint changes. Existing read access and the
staff/profile/photo, schedule, service and booking boundaries remain intact.

Production rollout is a separate owner decision. Preserve the shipped migration history. A merge
applies the four new forward migrations and deploys the Edge Functions within about 90 seconds,
in no enforced order:

1. [20261028100000_email_send_log.sql](../supabase/migrations/20261028100000_email_send_log.sql).
2. [20261028101000_email_send_log_deleted_booking.sql](../supabase/migrations/20261028101000_email_send_log_deleted_booking.sql).
3. [20261028185110_cms_single_writer_authority.sql](../supabase/migrations/20261028185110_cms_single_writer_authority.sql).
4. [20261104200000_public_cms_page.sql](../supabase/migrations/20261104200000_public_cms_page.sql):
   the Worker's bounded Contact read. A Worker that deploys before it reads the whole publication,
   as before, and serves the same page.

The logged senders `send-confirmation`, `send-auth-email`,
`admin-create-barber` and `external-cleanup` write to the email send log those two migrations
create; the [email rollout](operations/EMAIL_DELIVERY.md) describes a sender that deploys first. The authority
migration and `cms-studio` are safe in either order, and the frontend waits for the matching
`cms-studio` release digest; see [CMS compatibility/recovery](operations/CMS_RELEASE.md). The
updated upload gateway calls none of the legacy gallery/logo writer RPCs, which stay in this
release; dropping them is a later release after that gateway is verified live, as its
[README](../supabase/functions/upload-image/README.md) describes. These source files do not
establish which migrations or functions are hosted.

## Verification and deferred work

The static, unit, build, browser, startup, Edge Function, database and integration gates run in CI
on the stack PRs (#119 to #138) and on #104. Those runs do not certify production authentication,
delivery, migration or publication.

E1b part 2 and render-repair removal remain deferred until the owner's post-rollout publication
and a separate compatibility check of still-supported legacy inputs. A read-only production check
on 2026-11-10 found that the publication has not happened: the published `/about` English CSS still
holds legacy `@media (max-width:1440px)` id-only blocks, so every render-time `repairDesktopCss`
call stays. The Worker's frozen-header serving (`withFrozenActionLinks` and the frozen branch of
`planCmsRender`) also stays, and not only for that publication: `cms-studio` still accepts a
created page with `layout: 'independent'` or a `#cms-site-shell` element, so a publication that did
not pass Studio's adoption step can store one. One legacy path is gone: `renderCmsPage` no longer
restores per-mode inline styles on markup with the native marker. The four native routes never
reach `renderCmsPage`, and publication rejects `data-knc-*` attributes on every other path. Markup
that contains the marker text is still classified native there (one explicit mode, app bundle, no
reset or theme script) and served as the parser serialises it. Production migration
squashing/history repair, production deployment and CMS publication remain owner-dependent.
`presentation.regions` remains because validators and resource readers consume it. Archived PR90/91
reviews and the [maintenance handoff](MAINTENANCE_HANDOFF.md) remain historical evidence.
