# Repository Improvement Plan

Date: 2026-10-23, revised 2026-10-24. Repository: `barber/project` at HEAD `f15b79b` (production deployment `d5155e4c` from 2026-10-09 runs the same build).

## 1. Scope and method

This plan turns a four-wave read-only audit into ordered, verifiable work for future implementation sessions (Claude agents and the owner). It covers the public site and Cloudflare Worker, the admin panel and CMS Studio, the Supabase backend, Edge Functions, CI, tests, structure and docs. It answers the owner's twelve requirements (R1-R12) and the four owner-reported CMS examples plus the homepage flash.

How it was produced: Haiku scouts mapped the repository; seven Sonnet deep dives dug one concern each (cms-lifecycle, cms-parity, performance, replace-frontend, style-consistency, replace-backend, tests-structure); seven Opus validators re-opened every cited line at `f15b79b`, refuted, corrected and completed the findings using read-only production SQL and logs, GET-only probes, a local Supabase stack and headless browsers; Fable merged the validated output into this document. No repository file, production row or CMS document was written during the audit.

Evidence legend, used on every item:

| Tag        | Meaning                                                                                                          |
| ---------- | ---------------------------------------------------------------------------------------------------------------- |
| reproduced | A validator triggered the behaviour (production GET, local stack, harness or unit run) and recorded the numbers. |
| traced     | Confirmed by reading code, logs or stored data at `f15b79b`; not executed end to end.                            |
| unverified | Stated by a deep dive or inferred; a validator could not check it.                                               |

Ladder rungs (the owner's decision rule; stop at the first that holds): R1 delete, R2 stdlib, R3 native platform (HTML/CSS/browser API, Postgres, Supabase or Cloudflare built-in), R4 already-installed dependency, R5 mature library or free service, R6 minimum custom code. Effort sizes S/M/L/XL are relative, as the validators used them.

## 3. Guardrails for implementers

- Homepage pixel guard (R11): the hydrated homepage must stay pixel-identical. Before any boot-only change (PERF-2, PERF-3, PERF-6, PERF-8, PERF-18, LIB-2, LIB-9, PAR-3, PAR-5, PAR-11, PAR-14, PAR-15, STY-2, STY-5, STY-9, TST-16, LIFE-9), capture the PAR-18 "stored" baselines on HEAD (full page at 390/800/1280 px, light/dark x sv/en, reduced motion, About element shots) with the sanitised fixture presentation, and keep `tools/e2e/visual.spec.mjs` (8 baselines, maxDiffPixelRatio 0.001) green. A boot-only change may alter timing and intermediate states, never the final paint.
- CMS feature contract, preserved in full: draft with undo/redo and local backup with 3-way recovery; publish with revision+fingerprint CAS and the 409 merge flow; history restore of the whole document; validate for import and "Lås vy"; resources (upload, "Använd i utkastet", "Dölj från sidan", replace file, copy to category, archive/restore/trash/delete); pages (create a page with an editable body under the live homepage header, Duplicera, Ta bort, name, SEO, "Visa i meny"); devices Dator/Mobil; Ljus/Mörk per-mode CSS; separate SV/EN content with mirrored geometry; Style Manager, Avancerad CSS, resize handles, nudge, rotate/scale, hierarchical barber resize; theme panel (7 tokens), business panel, email design (templates and preview); legal pages with per-mode background editing. Acceptance tests: the owner scenarios in `tools/e2e/cms-owner.spec.mjs` (19 names, including custom-page-styles), `tools/e2e/cms-reported.spec.mjs` (1-legal-background, 2-new-page-editability, 2-owner-controls-survive-publication, 2-device-switch-styles), `tools/e2e/cms-new-page-mobile.spec.mjs`, `tests/integration/cmsAssetArchivePublish.test.ts:121-252`, and the new tests this plan adds. A change that turns one of them red is wrong until the owner has decided otherwise. Owner-changed tests (decisions 13 and 7/15 in section 9): the page-owned chrome assertions in `cms-owner.spec.mjs:666-834` and `cms-reported` 2-* are rewritten to assert the live header and an editable body; tests and contract text for the Mail delivery view are deleted with it.
- Homepage style reference (R10): the homepage is the only style reference. Every other user-facing page (terms, privacy, contact, 404, status screens, created pages, Google Calendar notice) uses the homepage's colours (including its dark colour), fonts and header look. Admin screens are out of scope except the staff auth pages (STY-8).
- Local only: implementation runs against the local Supabase stack and local Worker. Never use the production keys in `.env` for tests, never `supabase db push`, `supabase functions deploy`, `--linked`, `wrangler deploy` or a CMS publish to production. Production deploys and production data steps run only after the owner's explicit go, in the order of section 6.
- Net improvement (R7): every change deletes more than it adds, removes a failure mode, or is measurably faster, with features preserved. Code or dependencies added without a matching deletion are suspect and need the finding id that justifies them.
- Free services only. Items that would cost money (Workers Paid plan, calendar library licences) are owner decisions and are marked as such.
- Production safety: migrations first on the local stack and pgTAP; publish functions change in one migration; SQL and Edge validators must stay in step (deploy the tolerant validator before any writer omits a key, PAR-14); terminate looping PostgREST backends before and after the LIFE-3 migration; never run the legacy importer on tokenised legal files (STY-7); keep the static legal files as the no-CMS fallback.
- The ladder: when a subsystem is replaced, do not patch its internals; turn its confirmed defects into acceptance tests the replacement must pass. Validation at trust boundaries, data-loss prevention, security and accessibility basics are never "lazy" targets.

## 8. Rejected ideas

- Replace the admin schedule with Schedule-X, FullCalendar, EventCalendar or DayPilot Lite: 3.7x-7.6x the 13.8 kB gz chunk, no keyboard access to the time grid, paid resource views (LIB-12).
